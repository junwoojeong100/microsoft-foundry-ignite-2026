Re-run and failure-recovery criteria

  1. Retrying the same job: Using the same config, working folder, and private records, plan again → --apply → verify. It does not create existing accounts or roles twice or reset initial passwords. If the response to a remote user-creation POST is lost, the POST is not resent automatically.
  2. Conflicts and extra permissions: If the user ownership marker, RG tag, name, or region differs, or if unnecessary permissions exist, it stops. It does not arbitrarily adopt or modify existing resources or automatically revoke permissions. The operator reviews the cause and carries out a separate approved action.
  3. Lost records: If it finds an existing account but no password recovery record exists, it does not reset the password automatically. Restore an approved backup or follow a separate account recovery procedure. Do not retry by changing settings such as head count or region after creation, or by deleting the records.
  4. New event: Prepare with a new unique workshopId, but check whether the fixed UPNs and RGs are already in use. Resolve name collisions through an approved cleanup or a separate environment, and do not change the name format after applying. Run the same workshop sequentially, by one operator from one run folder, and do not apply it concurrently from other machines.
  5. Propagation and query errors: Permissions can take time to take effect. For 401/403, check the sign-in, Graph consent, operator roles, and scope, then wait for propagation and run the verification again. Do not hide errors or give participants a higher role.

  2. Prepare a unique UPN, display name, and initial password for each participant, and create the account with User type=Guest, enabled, and no Entra admin role. 2. Prepare the RPs, per-participant RGs, and user roles in the Azure Portal.

Required · The operator verifies the first sign-in and MFA registration on the actual training network.

You can prepare accounts, RGs, and RBAC in advance from an operator laptop, but this does not automatically prepare the participant's first successful authentication. Do not judge whether first-time registration is possible on the customer training network from the success of an account that had already registered MFA in the existing E2E, or from success on an employee network.

  1. Prepare new test accounts: Prepare 2 separate test-only Internal Guests that will not be assigned to customers, plus a test RG and the three roles. Start with accounts that have not registered MFA, and do not pre-register operator authentication methods on real customer accounts.
  2. First authentication on site: On the actual customer training network, device, browser, and phone, sign in with the test UPN and initial password and complete the account's own MFA registration and verification. The standard here is a password-change requirement of false; do not relax MFA or Conditional Access. Do not substitute success on an employee network, an instructor-only VPN/GSA, or the operator's environment.
  3. Sign in again and check access: Sign in again in a new browser session and confirm access to the target tenant, the subscription, and the account's own RG. For the two accounts' mutual RG and project access denial and for Playground → Agent → Traces, continue with the isolation and E2E checks above.

Record the policy and the result: If security info registration has an IP condition, the permission owner cross-checks the allowed Named locations against the public IPv4/IPv6 that Entra evaluated on the MFA registration request, not the location where the account was created. Hosted agent pre-deployment (optional Lab 12)

Participants do not deploy anything. The code agent that the operator deployed in advance is what they call and observe (Lab 12). You cannot create a Hosted agent in the portal (Code an agent in the New agent menu opens only an informational dialog); deployment goes through a code path such as REST, VS Code or azd. This repository's example uploads a source ZIP through REST; with no ACR, no azd provision and no new infrastructure, we verified deploying, invoking and deleting it in North Central US on 2026-11-18 (confirmed by re-running deploy_hosted_agent.sh end to end with a temporary agent name).
