Required lab · Sign in with the initial password and register your own MFA

Sign in with your own UPN and the initial password delivered separately. Accounts for a lab that lasts a few hours do not force a password change, and you complete MFA registration and verification yourself. UPN stands for User Principal Name, that is, a sign-in ID of the form username@domain. Do not confuse it with an email address or a GitHub username.

Open Azure Portal ↗ · Use InPrivate or a separate browser profile on an approved training network and device.

YOUR ACCOUNT AND ROLES

Check your account and permissions, then create resources inside your own RG.

The 9-step screens and video below show a basic Prompt Agent example carried out under these criteria. You can use the same account and permission criteria in other Foundry labs; the model, tools, and resources to create follow each lab's own text.

Handoff boundary: The operator hands off after providing accounts, RGs, RBAC, and subscription preconfiguration. Participants create the resources they need, such as Foundry, projects, models, and observability, themselves in their own RG. Entra account types and Azure RBAC are separate criteria, and being a Guest or a Member does not by itself give you permission to create resources in Azure.

Naming rule example: The UPN and RG you are assigned differ by event (for example, user01@<tenant initial domain> and rg-user01). Use the actual UPN and RG on your own assignment sheet, and do not type the long names from the recording as they are.

Account creation, subscription resource provider (RP) registration, role assignment, and wrap-up are tasks in the Foundry Operator guide. Participants do not receive operator roles or manage other participants' permissions.

Microsoft Copilot SDK 2.0 · The harness you embed in app code

It was previously called GitHub Copilot SDK (the rename began with the 2026-10-28 announcement, and package names may still contain GitHub). It is the interface for using the Microsoft Copilot harness in code; that harness was built by GitHub engineers and adopted as Microsoft's company-wide common foundation. It embeds a Rust-based harness in an app so you can build coding, work, and creative agents. One runtime handles multiple sessions while keeping each session's user, credentials, tools, files, and history separate. See Names explained for how the harness, the SDK, and the Foundry managed harness relate.

Announcement status: GA (Book of News, 2026-11-17). It is a different development path from the managed Copilot harness (Preview) in the Foundry portal.

Not run directly · based on official docs

Why there is no lab: Building an SDK app would require reviewing app implementation, authentication, and model and hosting costs, so we do not build or deploy one. In a shared runtime, app-level session isolation is not an OS or container security boundary, and untrusted code, shells, and user images need a separate sandbox.

Key changes in 2.0, the 6 execution architectures, and the relationship to Foundry

The host decides permissions: mode: "empty" starts without a host shell, file system, or default tools. The app decides which tools to provide and the availableTools allow list, and uses gitHubToken or gitHubTokenProvider to pass and refresh each session's user credentials.

Storage and resume: Session state is kept in external storage and resumed by using a journal together with sessionFs and createSessionFsProvider. The app is responsible for checking ownership so that it does not open another user's session.

Embedding and connection: Built on a C ABI, it supports TypeScript, Python, Go, .NET, Java, and Rust, and you choose among in-process embedding, child process, and shared service architectures. AHP (Agent Host Protocol), a separate public protocol, lets multiple clients connect to the same running session, and it is not a tool protocol that replaces MCP.

Managed and Programmed Training

With Managed, you submit data and settings and the model is trained as a managed service. MICROSOFT COPILOT HARNESS (PREVIEW)

The Microsoft Copilot harness (Preview) is an agent runtime that Foundry manages. It gives the agent built-in tools (Harness tools) such as file read, file write, web, shell, and subagents, and it uses a separate workspace for each conversation. The creation steps are similar to those of a regular Prompt Agent, but you must select the harness when you create the agent, and in the initial preview you cannot convert an existing agent into a harness agent (official docs).

Names explained · The Microsoft Copilot harness came from the GitHub Copilot harness, and this is how it connects to the SDK

Bottom line: The harness is the orchestration layer that wraps everything around the model (instructions, context, tools, execution environment, controls) so the agent can do its work. Microsoft adopted GitHub Copilot's harness, which the GitHub engineering team built, as a company-wide common foundation and calls it the Microsoft Copilot harness. The SDK that lets you use this harness in app code is the Microsoft Copilot SDK (formerly the GitHub Copilot SDK). A harness agent in the Foundry portal uses the same harness, with Microsoft operating it on your behalf.

Read your project's costs and create a token budget.

Every time you run an agent, tokens accumulate, and tokens translate directly into cost. At Ignite 2026, Foundry introduced Cost (Preview), which shows spending by project and agent on one screen, and Cost Control (Preview), which applies a warning or a block to spending and token budgets. In this lab, in your own project, you ① read usage and cost in Monitor → Cost, ② create a monthly token budget in Monitor → Cost Control, and ③ check what percentage of the budget the usage has reached. You create the budget as tracking-only (no warning or blocking action), so it does not affect requests. For other layers such as organization-wide cost, gateways, and Copilot Credits, see the cost management intro card for details.
